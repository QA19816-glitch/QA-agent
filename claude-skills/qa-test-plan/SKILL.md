# 测试计划生成器

输入需求文档、版本说明或功能描述，输出一份可直接使用的测试计划文档。

## 输入（任取其一或组合）

- PRD / 需求文档（文字或飞书链接）
- 版本号 + 变更说明
- 功能模块描述
- 历史 BUG 清单（用于风险识别）

## 输出结构（固定顺序）

### 1. 版本概述
- 版本号、测试周期（开始/结束日期）
- 被测系统（前端 H5 / 后台管理 / API）
- 测试目标：一句话说清楚本次测试要验证什么

### 2. 测试范围

| 模块 | 测试内容 | 是否新增 | 优先级 |
|------|----------|----------|--------|
| ...  | ...      | 是/否    | P0-P3  |

**范围外**：明确列出不测的内容及原因（如：支付真实链路、第三方 SDK 内部逻辑）

### 3. 测试策略

| 测试类型 | 方式 | 工具 | 覆盖目标 |
|----------|------|------|----------|
| 功能测试 | 手工 + 自动化 | Playwright | 核心流程 100% |
| 接口测试 | 自动化 | qa-api-runner | 新增/变更接口 |
| 兼容测试 | 自动化 | cross-browser-testing | Chrome/Safari/微信 |
| 性能测试 | 按需 | - | 首屏 ≤ 3s |
| 安全测试 | 按需 | security-scan-agent | OWASP Top 10 |

### 4. 用例分层

- **P0 冒烟（必跑）**：核心主流程，≤ 15 条，每次发布前必过
- **P1 核心回归**：新增功能 + 高频操作路径
- **P2 扩展回归**：边界值、异常路径、兼容场景
- **P3 探索测试**：非脚本自由探索，发现意外问题

### 5. 资源与排期

| 阶段 | 内容 | 负责人 | 工期 |
|------|------|--------|------|
| 用例设计 | 编写测试用例 | QA | X 天 |
| 环境准备 | 部署测试环境 | 开发 | X 天 |
| 功能测试 | 执行用例 | QA | X 天 |
| 回归测试 | BUG 修复验证 | QA | X 天 |
| 上线评审 | go/no-go 决策 | 全员 | 0.5 天 |

### 6. 准入标准（开始测试的条件）

- [ ] 测试环境部署完成，接口联调通过
- [ ] 冒烟用例通过率 ≥ 100%
- [ ] 无 P0 级未解决 BUG
- [ ] 需求文档评审完成，无重大歧义

### 7. 准出标准（发布的条件）

- [ ] P0/P1 用例通过率 ≥ 100%
- [ ] P2 用例通过率 ≥ 95%
- [ ] 无未关闭的 P0/P1 BUG
- [ ] P2 BUG 已评估，遗留项有跟进计划
- [ ] 性能指标达标（如有）

### 8. 风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|----------|
| 环境不稳定 | 中 | 高 | 提前 1 天验证环境，备用回滚方案 |
| 需求变更 | 中 | 中 | 变更需重新评估测试范围，延期排期 |
| 第三方依赖不可用 | 低 | 高 | Mock 替代，标注为"待真实环境验证" |

### 9. BUG 管理规范

- 缺陷系统：禅道（http://13.158.151.116:8088），产品：S基建项目
- 标题格式：`【Claude Code】现象 + 触发条件`，≤ 25 字，专业精准
- 严重度：P0（阻塞）/ P1（严重）/ P2（一般）/ P3（轻微）
- P0/P1 BUG 发现后 2 小时内通知开发负责人

## 执行规则

1. 如果输入是飞书文档链接，先用 `feishu-doc` skill 读取内容
2. 测试周期根据需求复杂度估算：小需求 3-5 天，中等 1-2 周，大版本 2-4 周
3. 排期表中工期填写工作日，不含周末
4. 风险表至少列 3 条，不能全是低概率
5. 输出为 Markdown，可直接粘贴到飞书文档
6. 如需同步到飞书，调用 `feishu-doc` skill 创建文档并授大王管理权限
