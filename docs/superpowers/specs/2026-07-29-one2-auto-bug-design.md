# One2 自动提 BUG 双平台路由设计

日期：2026-07-29  
状态：已确认，待实施计划

## 1. 背景

现有 Codex 自动提 BUG 能力以禅道为默认目标，已经覆盖缺陷取证、查重、标题与描述生成、截图上传、提交和保存后复核。现在需要在不破坏禅道能力的前提下，为 One2 质量管理平台增加同等闭环，并将未指定平台时的默认目标切换为 One2。

One2 当前入口为：

`http://192.168.113.115:32633/one2all/workspace/quality-management`

页面已确认具备缺陷列表、筛选、提 Bug 表单、复现材料上传和编辑/删除能力。创建表单强制关联具体需求，而不是只关联项目或项目集。

## 2. 目标

- 用户只说“提 BUG”时，默认提交到 One2。
- 用户明确说“提到禅道”时，继续走现有禅道自动提 BUG 链路。
- One2 与禅道使用独立技能、独立登录态、独立字段映射和独立校验，禁止双写、自动回退或跨平台补偿。
- One2 保留原自动提 BUG 的核心质量能力：证据整理、严格查重、需求匹配、附件上传、提交后回读和失败修复。
- 实施完成后通过一条可删除的测试 BUG 验证完整链路。

## 3. 非目标

- 不修改 One2 服务端或前端产品代码。
- 不把 One2 登录凭据、Cookie、令牌或密码写入仓库。
- 不将禅道数据同步到 One2，也不将 One2 数据同步回禅道。
- 不在 One2 提交失败时自动改投禅道。
- 第一版不实现独立的无浏览器 API 客户端；直接 API 适配留作后续优化。

## 4. 方案选择

采用“缺陷路由技能 + 两个平台独立适配技能”的结构：

1. `qa-defect-router` 负责根据用户指令选择目标平台。
2. `one2all` 负责 One2 的完整提单流程。这是面向用户和 Codex 技能目录的正式技能名。
3. `qa-zentao-defect-workflow` 保留现有禅道能力，但其通用“提 BUG”触发范围收窄为明确指定禅道。

One2 第一版使用 Codex 右侧可见浏览器执行。这样可以复用用户已经建立的 One2 登录态，并让用户看到需求选择、附件上传和提交过程。平台已观察到的 API 契约作为字段映射和后续 API 化依据，不在第一版直接接管认证。

## 5. 路由规则

按以下顺序判断：

1. 指令明确出现“禅道”时，只调用 `qa-zentao-defect-workflow`。
2. 指令明确出现“One2”、“one2”、“one2all”、“当前平台”或 One2 链接时，只调用 `one2all`。
3. 指令只包含“提 BUG”、“报 BUG”、“提交缺陷”等通用表达时，默认调用 `one2all`。
4. 同一指令同时明确要求两个平台时，先询问用户，不自动双写。
5. 任一平台失败后，保持在原平台处理或报告失败，禁止自动切换平台。

## 6. One2 字段映射

| 业务字段 | One2 字段 | 默认策略 |
| --- | --- | --- |
| 标题 | `title` | 只加一个 `【Codex自动化】` 前缀，最长 160 字 |
| 关联需求 | `requirement_id` | 根据需求文档、测试任务、页面模块和上下文自动匹配；无法唯一匹配时询问用户 |
| BUG 类型 | `bug_type` | 能从证据判断时自动分类，否则使用平台默认 `code_error` |
| 严重级别 | `severity_key` | 根据实际技术和业务影响独立判断；证据不足时询问用户，禁止固定使用 `p2`（一般） |
| 优先级 | `priority` / `priority_key` | 根据修复紧迫性独立判断；证据不足时询问用户，禁止固定使用 `medium` |
| 截止日期 | `due_date` | 仅在用户或需求明确给出时填写，否则清空为 `null` |
| 发现环境 | `found_environment` | 有明确实际环境时填写实际值；未提供或无法确定时默认填写 `test` |
| 操作系统 | `operating_system` | 从实际执行环境提取 |
| 浏览器 | `browser` | 从实际执行环境提取 |
| 开发负责人 | `assignee_user_id` | 默认留空，只有用户明确指定时填写 |
| 复现步骤 | `reproduction_steps` | 使用 One2 富文本结构，包含 `[步骤]`、`[实际结果]`、`[期望结果]` |
| 期望结果 | `expected_result` | 单独填写，保持与复现步骤中的期望一致 |
| 实际结果 | `actual_result` | 单独填写，保持与复现步骤中的实际结果一致 |
| 复现材料 | `reproduction_materials` | 上传成功后保存平台返回的材料 URL |
| 测试执行来源 | `source_execution_id` / `source_test_id` | 由测试执行或用例触发时传递，否则留空 |

当前前端已观察到：

- 创建缺陷：`POST /quality/bugs`
- 上传复现材料：`POST /quality/bugs/materials/upload`
- 材料上传必须同时提交 `file` 和 `requirement_id`

### 6.1 严重级别判定

严重级别反映缺陷已经造成或可能造成的实际影响，不等同于修复排期：

| One2 等级 | 判定标准 |
| --- | --- |
| `p0` 致命 | 系统或核心服务不可用；严重数据丢失/破坏；重大安全、资金或合规风险；影响范围广且无可行替代方案 |
| `p1` 严重 | 核心业务链路被阻断；关键功能大面积不可用；高频影响用户或业务目标；没有有效替代方案 |
| `p2` 一般 | 非核心功能异常、局部功能受损或结果错误；影响范围有限；存在可接受的临时绕行方案 |
| `p3` 轻微 | 文案、样式、轻度交互或低概率边界问题；不影响主要功能结果和核心流程完成 |

判定时必须记录依据，至少覆盖：影响用户/数据范围、是否阻断核心流程、是否存在数据/资金/安全风险、发生频率和是否有替代方案。不能因为表单默认值是“一般”就保留该等级。

### 6.2 优先级判定

优先级反映修复紧迫性，与严重级别分别判断：

| One2 等级 | 判定标准 |
| --- | --- |
| `urgent` 紧急 | 发布阻断、线上核心事故、安全/数据/资金风险，或必须立即止损的问题 |
| `high` 高 | 当前迭代核心目标受影响、高频用户问题、重要业务链路明显受损，应在当前迭代优先修复 |
| `medium` 中 | 常规缺陷，影响有限或存在绕行方案，可按正常迭代排期 |
| `low` 低 | 轻微体验、低频边界或优化型问题，可以进入后续待办 |

严重级别和优先级不得机械绑定。例如低频数据破坏问题可以“致命 / 高”，高频轻度体验问题可以“轻微 / 高”。若现有证据不能支持明确分级，提交前必须向用户确认，不能用默认值代替判断。

## 7. One2 完整数据流

1. 解析用户指令并由路由技能选择 One2。
2. 从用户描述、截图、录屏、日志和测试执行结果中提取缺陷事实。
3. 生成简洁标题、确定性复现步骤、实际结果和期望结果，并依据 6.1、6.2 的独立矩阵判定严重级别和优先级；判定依据不足时暂停询问。
4. 根据需求文档、测试任务、页面模块和历史上下文匹配具体需求。
5. 无法唯一匹配需求时，向用户展示候选项并等待选择；不得盲选。
6. 在 One2 缺陷列表中按标题关键词、影响页面、复现路径和根因查重。
7. 若命中同一根因，返回已有 BUG 编号和重复依据，不创建新记录。已关闭缺陷再次出现时，只有能证明为回归问题才允许新建并关联旧缺陷。
8. 打开可见的 One2 提 Bug 页面，先选择关联需求，再上传复现材料。
9. 填写全部字段并提交。
10. 回读缺陷列表和详情，确认编号、标题、关联需求、复现步骤、实际结果、期望结果及附件均已保存。
11. 附件为图片或视频时，必须确认详情页可以正常预览；图片需具备非零自然尺寸和可见布局尺寸。
12. 只有全部校验通过后，才向用户报告提交成功并返回 BUG 编号。

## 8. 查重标准

不能只比较标题。以下信息同时高度相似时视为重复：

- 相同页面、模块或功能流。
- 相同触发条件和最小复现路径。
- 相同实际结果或错误表现。
- 相同或高度可能相同的根因。

若只是标题相似但影响对象、触发条件或根因不同，则不是重复。自动化误建重复 BUG 时，应立即删除或按平台规则关闭重复记录，并报告保留和清理的编号。

## 9. 异常处理

- **登录失效**：停在 One2 登录页并请用户重新登录；不读取或导出密码，不切换禅道。
- **需求不唯一**：展示候选需求并询问；不得自动选择最相似项。
- **查重命中**：返回已有编号和依据；不执行创建。
- **附件上传失败**：重试一次；仍失败则停止提交并报告，不降级为无证据 BUG。
- **提交结果不确定**：先按标题和时间回查，禁止重复点击提交。
- **字段回读缺失**：尝试通过编辑页修复并再次回读；修复失败则报告不完整。
- **附件预览失败**：重新上传或修复材料引用；未验证可见前不得报告成功。
- **测试 BUG 删除失败**：保留编号并明确报告，不隐藏残留数据。
- **平台不可用**：报告 One2 不可用；禁止转投禅道。

## 10. 可见浏览器约束

- One2 网站操作默认使用 Codex 右侧可见浏览器。
- 复用该浏览器的持久登录态，不读取 Cookie、本地存储或密码管理数据。
- 所有点击、输入、选择和上传均基于当前页面快照中的唯一控件。
- 提交前确认目标平台域名、关联需求和标题；提交后必须重新读取页面状态。
- 中文测试站点使用中文环境，不从英文浏览器环境产生文案或国际化缺陷。

## 11. 验收测试

### 11.1 路由测试

- “提 BUG”只进入 One2。
- “提到 One2”只进入 One2。
- “提到禅道”只进入禅道。
- 同时指定两个平台时暂停询问。
- One2 失败时不触发禅道。

### 11.2 分级规则测试

- 核心服务不可用、无替代方案时不能判为“一般”。
- 数据、资金或安全风险必须进入高严重级别判断。
- 非核心局部问题且存在绕行方案时不能机械判为“致命”。
- 高频体验问题允许出现“轻微 / 高”，证明严重级别和优先级没有机械绑定。
- 输入信息不足时必须触发确认，不得静默使用“一般 / 中”。

环境字段还需验证：未提供发现环境时保存为 `test`；明确提供其他环境时保留实际值，不得被默认值覆盖。

### 11.3 One2 端到端测试

1. 选择一个明确、安全的测试需求；如果没有合适的测试需求，提交前询问用户。
2. 创建标题为 `【Codex自动化】One2自动提BUG链路验收` 的测试 BUG。
3. 填写步骤、实际结果、期望结果、严重级别和优先级。
4. 上传一张有效测试截图作为复现材料。
5. 提交后获取 BUG 编号。
6. 在列表和详情页回读所有关键字段。
7. 验证截图资源可访问且详情页可见预览。
8. 删除测试 BUG。
9. 再次搜索标题和编号，确认记录已删除。

只有步骤 1-9 全部通过，才认为 One2 自动提 BUG 功能已打通。
