# 高风险、多来源测试用例设计规则

在输入来源超过一份、材料存在冲突、功能风险较高，或交付物用于正式评审和发布决策时使用本规则。

## 输入盘点

列出实际使用的材料，例如需求、用户故事、验收标准、PRD、原型、接口说明、技术方案、变更清单、历史缺陷、线上问题和回归重点。

对每项关键信息标明：

- 已确认事实：来源明确且不同材料无冲突。
- 来源冲突：用“来源 A / 来源 B”说明差异，不静默选边。
- 当前假设：为了形成可执行初版而作出的合理假设。
- 待确认缺口：会影响高风险覆盖、发布判断或预期结果的信息。

## 风险与优先级

优先级同时考虑业务影响和失败概率：

- P0：核心主链路、发布阻塞、资金/数据/安全风险、无可接受绕行方案。
- P1：重要业务路径、高频使用、关键集成或历史高缺陷区域。
- P2：常规功能、有限影响异常和普通兼容性覆盖。
- P3：低频边缘、轻微体验或低风险补充覆盖。

不要因为想让数量均匀而分配优先级。半天或更短执行窗口下，优先保留 P0，并明确本轮未覆盖范围。

## 追踪规则

每条用例必须绑定具体需求、故事、规则或风险引用。没有正式 ID 时，生成稳定标签，例如 `REQ-LOGIN-LOCK`、`RISK-OTP-REPLAY`，并注明“派生标签”。

追踪矩阵至少包含：

| 需求或风险引用 | 覆盖的用例ID | 覆盖类型 | 缺口备注 |
| --- | --- | --- | --- |

追踪矩阵中的用例 ID 必须存在于用例表中；表中的关键用例也应能反查来源。

## 覆盖门槛

除非用户主动缩小范围，高风险行为应覆盖：

- 正向：合法角色、合法状态和有效数据完成目标。
- 异常：失败依赖、无效输入、无权限、超时、重试失败和回滚。
- 边界：最小值、最大值、临界状态、空值、重复提交、过期和并发。
- 回归：历史缺陷、相邻模块、上下游集成和旧数据兼容。

根据业务选择等价类、边界值、判定表、状态迁移、场景法、Pairwise 或错误推测，不机械套用所有方法。

## 用例要求

每条用例必须具备：

- 稳定且唯一的用例 ID。
- 单一、明确的测试目的。
- 可复现的前置条件和测试数据。
- 按动作顺序编号的测试步骤。
- 与步骤对应、可观察且可判定的预期结果。
- 真实反映影响和风险的 P0-P3 优先级。
- 具体追踪引用；不得写成笼统的“见需求文档”。

禁止编造用户未提供的字段、接口路径、错误码、环境或根因。未知信息使用“待确认”，并说明它对覆盖的影响。

## 默认正式交付顺序

1. 文档标题。
2. 文档信息：范围、环境、版本、来源和假设。
3. 测试用例汇总：数量、优先级、模块和风险热点。
4. 按模块、子模块拆分的测试用例表。
5. 需求/风险追踪矩阵。
6. 假设、信息缺口和阻塞确认项。
7. 冒烟子集、建议执行顺序和自动化候选。

用户仅要求少量冒烟用例时，保留关键表格与必要说明即可，不要过度工程化。

## 交付自检

- 高风险路径是否存在正向、异常和边界覆盖，或有明确省略理由？
- 是否区分了事实、冲突、假设和缺口？
- 用例是否能由另一位测试人员独立执行？
- 预期结果是否可以明确判定通过或失败？
- 追踪矩阵与用例 ID 是否一致？
- 是否避免了重复凑数和无关的通用测试理论？
